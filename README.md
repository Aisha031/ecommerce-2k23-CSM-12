# RootRemedy

An online storefront for herbal & wellness products. See `docs/` for sprint
design documents: Sprint 1 (architecture & scope) and `docs/SPRINT_2.md`
(catalog data foundation — this sprint).

## Local setup

1. **Create a virtual environment and install dependencies**
   ```bash
   python -m venv .venv
   source .venv/bin/activate        # Windows: .venv\Scripts\activate
   pip install -r requirements.txt
   ```

2. **Environment variables** — copy `.env.example` to `.env` and fill it in
   (or export the same variables in your shell). At minimum for local dev
   against Postgres:
   ```
   POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_HOST, POSTGRES_PORT
   ```
   If you don't have Postgres running yet, you can skip these — `config/settings.py`
   falls back to a local SQLite file (`db.sqlite3`) so migrations, tests, and
   the seed command all work without a database server. This is a local
   convenience only; the project's actual database choice (justified in
   Sprint 1) is PostgreSQL, and CI/production should always set the
   `POSTGRES_*` variables. Never commit a real `.env` file.

3. **Run migrations**
   ```bash
   python manage.py migrate
   ```

4. **Create an administrator account** (for the catalog admin API and
   `/admin/` site)
   ```bash
   python manage.py createsuperuser
   ```
   A superuser automatically has `is_staff=True`, which is what
   `IsCatalogAdministrator` checks (see `catalog/permissions.py`).

5. **Load reproducible demo data** (§9 of the Sprint 2 brief)
   ```bash
   python manage.py seed_catalog
   ```
   This creates two category levels, three products (one with two real
   variants), four SKUs, and one deliberately *missing* variant combination.
   It also creates a `catalog_admin` / `demo-pass-123` staff account so you
   can hit the admin API immediately.

6. **Run the server**
   ```bash
   python manage.py runserver
   ```

## Running tests

```bash
python manage.py test
```

Covers: product/SKU creation with required fields, duplicate slug/SKU
rejection, category hierarchy validation (including cycle prevention),
variant/SKU combination and stock rules, and authorization failures on every
administrative endpoint. See `docs/SPRINT_2.md` §7 for the recorded result.

## Administration API

Base path: `/api/v1/admin/`. All routes require an authenticated `is_staff`
account (session or basic auth). Full route table, request/response shapes,
and example calls are in `docs/SPRINT_2.md` §4.

## Known limitation of this checkout

This repository was prepared in a sandboxed environment with no package-index
access, so migrations were written by hand rather than generated by
`makemigrations` against a live Postgres instance. Run
`python manage.py makemigrations --check` after `pip install`-ing on a normal
machine to confirm the hand-written migrations match the models before your
first real deploy; if it reports drift, let `makemigrations` generate a
correction migration rather than hand-editing the existing one.
